# Feature Specification: 网络安全学术研究 Deep Research 系统

**Feature Branch**: `001-deep-research-agent`

**Created**: 2026-09-29

**Status**: Draft

**Input**: User description: "面向网络安全学术研究，构建 Multi-Agent Deep Research 系统，覆盖四类任务（选题构思 / 方法差分 / 实验与主张验证 / 审稿意见回应）。输入为自然语言研究请求，经澄清收敛为 ResearchBrief（10 字段契约）；输出为统一骨架的可追溯研究报告（含任务专属第 3 节）。核心能力：需求澄清、递归检索与证据追溯、口径归一与可比性校核、证据驱动写作与审阅闭环、长流程可恢复。契约详见 docs/contracts/，端到端用例见 docs/cases/。"

## User Scenarios & Testing

### User Story 1 - 研究请求收敛与 ResearchBrief 冻结 (Priority: P1)

研究人员提交一个开放研究请求（可自选任务模式，或交由系统判断）。系统只针对会改变检索计划、可接受证据、可支持结论或验证方案的缺失信息发起澄清，收敛后冻结一份结构化 ResearchBrief，作为后续调研的依据。

**Why this priority**: 这是所有任务类型的统一入口。没有冻结的 ResearchBrief，后续检索范围与证据覆盖都无法评估。

**Independent Test**: 单独交付时，输入任意开放研究请求，验证系统能识别任务类型、仅对关键缺失发起澄清，并冻结含 10 字段的 ResearchBrief。

**Acceptance Scenarios**:

1. **Given** 一个开放请求且缺失信息会改变检索/证据/结论/验证，**When** 系统分析，**Then** 系统发起针对性澄清（每轮 1–2 个高信息增益问题）。
2. **Given** 澄清完成或信息已足够，**When** 系统收敛需求，**Then** 系统冻结含 10 字段的 ResearchBrief。
3. **Given** 缺失信息为非关键项，**When** 系统处理，**Then** 系统采用可披露的保守默认值，而非无限追问。

---

### User Story 2 - 选题构思（idea_exploration）(Priority: P2)

研究人员选择「找研究问题」。系统按 ResearchBrief 检索多方向已有证据，识别在公开数据与有限算力下可验证的研究缺口，提出候选研究问题并评估可行性。

**Why this priority**: 选题构思是研究生命周期的起点，也是系统首个可独立验证的任务类型。

**Independent Test**: 给定一份 idea 类型的 ResearchBrief，验证系统能产出含「问题 / 可验证假设 / 所需数据 / 新颖性风险 / 可行性」的候选问题卡与推荐问题。

**Acceptance Scenarios**:

1. **Given** 冻结的 idea 型 ResearchBrief，**When** 系统调研，**Then** 系统输出候选问题卡，每张含问题、可验证假设、所需数据/资源、可行性。
2. **Given** 多个候选问题，**When** 系统评估，**Then** 系统给出推荐问题与最小验证闭环。

---

### User Story 3 - 方法差分（method_differentiation）(Priority: P2)

研究人员选择「论证方法差异」。系统比较候选技术路线，产出最近邻工作比较矩阵，并判断拟议方案能否与最相近工作形成可验证差异。

**Why this priority**: 方法差分直接服务技术路线论证，是网络安全选题的核心决策支撑。

**Independent Test**: 给定一份 method 型 ResearchBrief，验证系统能产出含各路线「输入 / 机制 / 输出 / 限制」的比较矩阵与可验证差分主张。

**Acceptance Scenarios**:

1. **Given** 冻结的 method 型 ResearchBrief，**When** 系统比较候选路线，**Then** 系统输出最近邻工作比较矩阵。
2. **Given** 存在量化结果，**When** 系统比较，**Then** 系统仅在可比口径下给出差值或结论，口径不一致时不强行比较。

---

### User Story 4 - 实验与主张验证（evaluation_design）(Priority: P2)

研究人员选择「设计实验」。系统针对检测、溯源、泛化等主张设计实验协议，产出「协议—指标—结论」映射，并明确每个协议能支持与不能支持的结论。

**Why this priority**: 验证设计把主张变成可执行的实验，是可行性论证的落点。

**Independent Test**: 给定一份 eval 型 ResearchBrief，验证系统能产出每个主张的协议、对照组、指标、能支持与不能支持的结论。

**Acceptance Scenarios**:

1. **Given** 冻结的 eval 型 ResearchBrief，**When** 系统设计实验，**Then** 系统输出每个主张的实验协议、对照组与指标。
2. **Given** 各协议，**When** 系统界定边界，**Then** 系统明确每个协议能支持与不能支持的结论。

---

### User Story 5 - 长流程恢复与进度可见 (Priority: P3)

长时间运行的研究任务在返工或中断（网络断开、服务重启、人工中断）后，研究人员能从中断前的最近检查点恢复，不重复已完成工作；执行过程中能实时看到进度与阶段状态，审阅版本不错位。

**Why this priority**: 研究链路长、耗时久，中断恢复与进度可见是可用性前提；否则长任务会因一次中断而前功尽弃。

**Independent Test**: 在任务执行中途人为中断，验证系统能从最近检查点恢复、不重复已完成检索与写入，且过程进度实时可见。

**Acceptance Scenarios**:

1. **Given** 执行中的长任务被中断，**When** 研究人员恢复，**Then** 系统从最近检查点继续，不重复已完成工作。
2. **Given** 任务执行中，**When** 阶段推进，**Then** 系统实时推送进度与阶段状态。
3. **Given** 多轮修订，**When** 系统持久化进度与版本，**Then** 审阅版本不错位。

---

### Edge Cases

- 研究请求极度开放、无法收敛时，如何处理？（引导性澄清，且轮数有上限）
- 检索结果为空或证据严重不足时，如何呈现？（显式标注证据缺口，而非编造证据）
- 检索/补查超出预算时，如何降级？（预算内返回已有证据并标注缺口）
- 同一来源被多次命中时，如何避免重复？（按来源定位去重）
- 指标口径不一致时，如何避免错误比较？（标记不可比并记录原因，不强行比较）
- 任务在写入报告中途崩溃，如何保证不半写？（从检查点恢复、幂等写入）
- 回流迭代达到上限仍未闭环，如何处理？（收紧结论边界并列入风险，而非伪装通过）
- 用户主动取消，如何传递并安全停止？

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 接收自然语言研究请求，识别任务类型（选题构思 / 方法差分 / 实验验证 / 审稿回应），对不确定的情况可由系统判断。
- **FR-002**: 系统 MUST 仅在未确定信息会改变检索计划、可接受证据、可支持结论或验证方案时发起澄清。
- **FR-003**: 系统 MUST 每轮澄清只提 1–2 个高信息增益问题，并设轮数上限；非关键缺口 MUST 采用可披露的保守默认值。
- **FR-004**: 系统 MUST 将收敛后的需求冻结为 ResearchBrief，包含 10 字段：task_type、decision_goal、research_object、scope、comparison_scope、claims_to_verify、evidence_requirements、conclusion_boundary、deliverable、assumptions。
- **FR-005**: 系统 MUST 支持跨轮澄清（持久化澄清历史、待答问题与 Brief 草稿，供后续轮次回复）。
- **FR-006**: 系统 MUST 支持从论文、网页、本地知识库多源检索证据。
- **FR-007**: 系统 MUST 针对关键论断递归追溯原始来源（原始论文、数据集文档、官方代码），而非停留在摘要或二手转述。
- **FR-008**: 系统 MUST 按来源定位去重（同一来源同一位置只保留一条证据），并保留来自不同来源的多源佐证。
- **FR-009**: 系统 MUST 将证据组织为可回溯证据链，每条证据带来源定位，并记录证据对论断的支持 / 反驳 / 限制关系。
- **FR-010**: 系统 MUST 在查询预算内识别证据缺口并发起定向补查；无法补齐的缺口 MUST 显式标注为待验证，而非用推断补全。
- **FR-011**: 系统 MUST 对量化比较内容归一评测条件（任务、数据集版本、切分协议、指标定义、告警预算、基线）并判断可比性（可比 / 部分可比 / 不可比）。
- **FR-012**: 系统 MUST NOT 在口径不一致时强行比较或制图；不可比 MUST 记录原因。
- **FR-013**: 系统 MUST 基于可比指标执行比较计算或制图，产物可回链到输入证据。
- **FR-014**: 系统 MUST 按统一报告骨架撰写报告，覆盖 ResearchBrief 规定的章节与论断。
- **FR-015**: 系统 MUST 让每个关键结论绑定其证据引用，可回链到证据与来源定位。
- **FR-016**: 系统 MUST 逐项复核结论、引用与适用条件，并将证据缺口、口径冲突、表述越界分别回流至补查、重算或修订。
- **FR-017**: 系统 MUST 限定回流迭代次数；达到上限仍未闭环时 MUST 收紧结论边界并列入风险清单，而非伪装为已通过。
- **FR-018**: 系统 MUST 按任务类型输出专属交付：选题构思 → 候选问题卡；方法差分 → 比较矩阵与差分主张；实验验证 → 协议-指标-结论映射。
- **FR-019**: 系统 MUST 支持长任务从最近检查点恢复，且不重复已完成的检索与写入（幂等）。
- **FR-020**: 系统 MUST 在任务执行中实时推送进度与阶段状态。
- **FR-021**: 系统 MUST 持久化任务进度、返工目标与报告版本，避免审阅版本错位。
- **FR-022**: 系统 MUST 支持用户注册（邮箱 + 密码，密码哈希存储，禁止明文）。
- **FR-023**: 系统 MUST 支持用户登录并签发认证凭证（JWT 或 cookie 会话）。
- **FR-024**: 系统 MUST 校验受保护请求的认证凭证，并将研究会话归属于对应用户。

### Key Entities

- **ResearchBrief（研究任务书）**：冻结的 10 字段契约，定义研究范围、比较对象、可接受证据、结论边界与交付形式。
- **SectionPlan（章节计划）**：逐章节的目标、论断、检索子问题、检索锚点、证据需求与分析需求。
- **Claim（研究论断）**：需由证据支持、限制或反驳的核心判断，附成立条件。
- **Evidence（证据）**：带来源定位的最小引用单元（来源、页码/表格、原文片段）。
- **ClaimEvidenceLink（论断-证据关系）**：记录证据对论断的 supports / refutes / limits 关系。
- **SourceRecord（来源登记）**：来源的类型、版本、层级与获取记录，同一来源只登记一次。
- **QuantitativeObservation（量化观察）**：结果表单元格或段落数值的结构化投影，回链到证据。
- **ComparableMetric（可比较指标）**：口径归一后的指标，附可比性结论（可比/部分可比/不可比）。
- **AnalysisArtifact（分析产物）**：基于可比指标的计算/图表，回链输入指标与证据。
- **DraftSection / DraftClaimBinding（草稿与绑定）**：章节草稿及结论到证据/产物的显式绑定。
- **CriticFeedback（审阅反馈）**：定位到具体对象的审阅问题与返工路由（补查/重算/修订/收紧边界）。
- **交付物**：候选问题卡（idea）/ 比较矩阵与差分主张（method）/ 协议-指标-结论映射（eval）。
- **User（用户）**：账号（邮箱、密码哈希）；研究会话归属于用户。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 提交研究请求后，系统在不超过 3 轮澄清内冻结 ResearchBrief（或对非关键项采用保守默认）。
- **SC-002**: 报告中每条关键结论与引用均可回链到带定位的证据（可溯源率 100%，无法溯源处显式标注）。
- **SC-003**: 口径不一致的指标被识别并标记不可比，报告中无不加说明的跨口径比较。
- **SC-004**: ResearchBrief 规定的关键论断在报告中被覆盖（未覆盖的论断显式标注为证据不足）。
- **SC-005**: 证据缺口被识别并补查或标注为待验证，而非静默产出无依据结论。
- **SC-006**: 任务中断后从最近检查点恢复，重复检索与重复写入为 0。
- **SC-007**: 相比人工调研，形成同等标准可编辑初稿的时间缩短至少 50%。
- **SC-008**: 输出报告符合统一骨架 + 任务专属第 3 节的结构要求。

## Assumptions

- 目标用户为网络安全方向的学术研究人员（含课题组成员），具备领域知识，可做最终人工复核；系统定位为辅助而非替代人工判断。
- v1 覆盖 4 类任务；其中 reviewer_response 的报告模块与交付要素待定义，暂缓细化。
- 交付形态默认为可部署的 Web 服务（含实时进度展示）。
- 数据源默认为论文检索、网页搜索、本地知识库三类；具体接入的数据源在 plan 阶段确定。
- 多智能体职责分解（澄清 / 检索 / 口径归一 / 分析执行 / 撰写 / 审阅）与工作流编排、检查点持久化、进度推送等技术机制属实现方案，在 plan 阶段落地，不作为本 spec 的功能约束。
- v1 提供基础用户认证（注册/登录），不包含复杂 RBAC / 多租户权限体系（面向课题组内使用）。
- 完整契约参考见 docs/contracts/，端到端用例见 docs/cases/；评测契约见 docs/architecture/07-evaluation.md（暂不实现）。
- 完整设计源（Agent 职责 / 状态 schema / 数据流）见 docs/architecture/，将在 plan 阶段消费。
