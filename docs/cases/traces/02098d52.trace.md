## 对系统设计的启示（为什么这份轨迹有「妙用」）

1. **先加载契约，再检索**：前 8 步全部在读 contracts/骨架，而不是直接搜——这正是 ChiefArchitect 的
   SectionPlan 要先冻结、DeepScout 才检索的原因。
2. **检索是分主题批次的**：数据集事实（9,10,14,19）→ 方法（11,16,22,24）→ 跨版本（12,25）→
   综述（18,21）→ 溯源/评测（15,20,26）。DeepScout 的 `sub_questions` 应按这种粒度生成。
3. **检索 query 的写法**：关键词密集 + 精确锚点（如 `"Cert Dataset Decade"`、`"Bridging the gap"`、
   `Glasser Lindauer 2013`）——不是泛泛的"insider threat"，而是直接命中具体论文/数据集。这给
   DeepScout 的「检索锚点」（retrieval_anchors）提供了真实范例。
4. **一次 case 一次写**：写 case-1 后，为 case-2/3 又补了 8 次针对性检索（弱监督/协议/校准/指标），
   说明「检索 → 写作」是交织的，不是一次性检索完再写。
5. **WebFetch 只用了 1 次**（官方数据集页），其余靠 WebSearch 摘要 + 交叉核对——对应"摘要用于筛选、
   高价值原文才 fetch_document"的检索策略。
