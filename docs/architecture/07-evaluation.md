# 面向网络安全学术研究的 Deep Research：离线评测设计

> 定位：本文记录 DeepResearch 项目的首版离线评测框架。当前只冻结两部分：领域任务集与研究结果质量评估。研究过程质量、业务效果与最终量化效果数值，待系统实现和实际试验后补充。

## 1. 评估目标与边界

系统面向网络安全学术研究中的选题构思、技术路线论证和验证方案设计。评测的对象不是通用网页问答能力，而是：系统能否围绕一个范围受控的研究请求，形成证据可回溯、结论条件明确、可供研究者继续修改的调研产物。

首版评测集定位为**小规模领域课题调研任务集**，不宣称构成通用 Deep Research Benchmark。任务、资料快照、Gold 标注和模型版本均应固定，避免开放网页内容变化导致结果不可复现。

评估目标分为三类：

1. **研究质量**：报告是否覆盖关键论断，结论是否由适当证据支撑，是否交代成立条件与局限。
2. **研究过程**：检索和补查是否有效、来源是否足够可靠、工作流是否稳定可追溯。此部分待后续定义。
3. **业务效果**：报告是否帮助研究者进行技术路线论证或验证设计，以及相对人工调研的时间成本。此部分待后续定义。

每类目标再按判分手段选择 Code-based、Model-based 与 Human grader；三者不是互斥的评估层级。

| 评估对象 | Code-based grader | Model-based grader | Human grader |
| --- | --- | --- | --- |
| 研究质量 | 引用 ID、来源定位、必填字段、交付结构校验 | 证据是否支撑论断、覆盖与结论边界 rubric | 抽样复核 Gold 与 LLM Judge 的一致性 |
| 研究过程 | 待后续定义 | 待后续定义 | 待后续定义 |
| 业务效果 | 待后续定义 | 待后续定义 | 目标研究者的可用性与时间成本判断 |

## 2. 领域任务集

### 2.1 规模与任务类型

首版拟构建 10 条网络安全 / AI 安全学术研究任务，覆盖以下三类需求：

| 类型 | 数量建议 | 典型交付 |
| --- | ---: | --- |
| `idea_exploration` 选题构思 | 3 | 研究缺口、候选研究问题、可验证假设与可行性风险 |
| `method_differentiation` 方法差分与技术路线论证 | 4 | 方法比较矩阵、最相近工作、适用条件、差分主张与局限 |
| `evaluation_design` 实验与主张验证设计 | 3 | 主张—协议—指标映射、对照组、验证计划与结论边界 |

领域限定在网络安全和 AI 安全相关议题，例如内部威胁检测、提示注入防护、RAG 知识库投毒、间接越狱、LLM 越狱鲁棒性与安全数据处理。限定领域是为了让 Gold 标注具备研究者可核验的质量，而非宣称系统已泛化到任意开放课题。

### 2.2 难度划分

难度不以是否跨领域作为主标准，而依据完成研究论证所需的证据与推理复杂度划分。

| 难度 | 判定特征 |
| --- | --- |
| 基础 | 单一技术路线，少量原始论文即可回答，结论与适用条件较明确。 |
| 中级 | 需要比较两至三条路线，核对数据集、版本、实验协议、指标或实现条件。 |
| 高级 | 需要在论文、数据集、代码仓库或标准之间交叉取证；存在冲突证据、条件不一致或不可直接外推的风险。 |

每类任务应覆盖基础、中级和高级样本。高难度案例的重点是考察“能否指出不可直接比较或需要补证”，而不是强迫系统给出单一确定结论。

### 2.3 单条任务包

每条评测任务由以下内容组成：

```text
TaskPackage
├── research_request         # 原始研究请求
├── frozen_research_brief    # 冻结后的 ResearchBrief
├── corpus_snapshot          # 固定资料范围、抓取时间与版本
├── gold_units               # 关键论断—条件—证据单元
├── known_limitations        # 已知局限、冲突点与不可作出的结论
└── deliverable_requirements # 任务特定的报告与交付要求
```

评测时必须固定资料快照、模型版本、预算、报告模板和 baseline 的输入范围；否则无法将差异归因于 DeepScout 的递归追溯、Critic 的审阅回流或其他具体模块。

## 3. Gold 标注契约

### 3.1 最小标注单元：论断—条件—证据

Gold 不应只是一组 `top-K facts` 或唯一答案 URL。学术研究存在多条合理证据路径，真正需要约束的是：报告中的关键研究论断，必须在其成立条件下由可接受来源支撑。

```text
GoldUnit
├── unit_id
├── claim                    # 关键研究论断
├── conditions               # 数据集、版本、协议、指标、假设等成立条件
├── acceptable_evidence_sets # 一个或多个可接受 Evidence 集合
├── required_source_tier     # 例如原始论文、官方数据集页、代码仓库、标准
├── expected_stance          # supports / limits / refutes / uncertain
└── limitation               # 不能外推或尚待验证之处
```

示例：

```text
claim:
  时序行为表示路线在跨版本内部威胁检测中具有泛化潜力。

conditions:
  CERT r6.2；跨版本划分；Recall@固定告警预算。

acceptable_evidence_sets:
  - 论文 A 的表 4 与实验设置段落
  - 论文 B 的对应实验结果与代码仓库配置

limitation:
  不能把 CERT 上的结果直接外推为生产环境效果。
```

一个 GoldUnit 可对应多套可接受证据，不要求系统复现人工标注者唯一的检索路径。

### 3.2 标注与复核

1. 先由具备领域知识的标注者为每项任务列出关键论断、条件、可接受证据与局限。
2. 第二位标注者抽样核验争议单元，重点检查条件是否被遗漏、证据是否真能支撑论断。
3. 对存在合理分歧的论断保留 `uncertain` 或多套 `acceptable_evidence_sets`，不要强行制造唯一标准答案。
4. 在正式评测前冻结 Gold 版本；若资料发生变化，应形成新快照和新版本，而不是覆盖旧标注。

## 4. 研究结果质量指标

### 4.1 关键论断与条件覆盖率

设某任务的 Gold 单元集合为 $G$，系统输出中被有效覆盖的单元集合为 $C$。只有报告陈述了该论断、交代必要条件，并引用了可接受证据时，才计为有效覆盖。

$$
\mathrm{ClaimConditionCoverage} = \frac{|C|}{|G|}
$$

该指标避免只写“方法 A 优于方法 B”便获得覆盖分，而忽略“在哪个数据集、什么协议、以什么指标成立”。

### 4.2 引用支撑率

对报告中带引用的关键陈述逐条检查：引用是否可回链，且引用原文是否支持相应陈述及其条件。

$$
\mathrm{CitationSupportRate} =
\frac{\text{被引用证据实际支撑的关键陈述数}}
{\text{已检查的带引用关键陈述数}}
$$

代码 grader 可先校验 Evidence ID、来源定位和引用范围；模型或人工 grader 再判断“支持”这一语义关系。

### 4.3 事实正确率与幻觉率

从报告中抽取可验证的关键陈述，重点覆盖数值、时间、因果关系和方法比较结论。逐项标记为 `correct`、`disputed`、`incorrect` 或 `unverifiable`。

$$
\mathrm{FactCorrectRate} =
\frac{\text{correct 的可验证关键陈述数}}
{\text{可验证关键陈述数}}
$$

$$
\mathrm{HallucinationRate} =
\frac{\text{incorrect 或无有效出处支撑的关键陈述数}}
{\text{关键陈述总数}}
$$

`disputed` 与 `unverifiable` 应单独报告，不能为了得到漂亮数字强行归入正确或错误。

### 4.4 来源质量与溯源性

该项关注系统是否追到支撑技术判断的原始资料，而非仅使用摘要、二手转述或低质量聚合页。

建议至少记录：

- 关键论断引用中原始论文、官方数据集页、官方代码仓库或标准的占比；
- 关键论断是否存在可定位的来源片段；
- 是否只依赖单一来源类型；
- 是否使用低质量或无法追溯的来源支撑核心结论。

首版可先将其实现为来源等级合格率和来源定位完整率，后续再讨论是否引入加权来源质量分。

### 4.5 结论边界与风险项覆盖

对任务要求说明限制、不可比较条件或风险清单的案例，检查报告是否：

1. 明确写出关键不确定性；
2. 避免将受限实验结果外推为通用或生产结论；
3. 对证据不足处给出待验证项，而不是补写确定性结论。

可定义结论越界率：

$$
\mathrm{OverclaimRate} =
\frac{\text{超出证据或条件范围的关键结论数}}
{\text{关键结论总数}}
$$

该指标尤其适用于网络安全研究中的数据集代理、攻击假设和真实部署差异。

### 4.6 交付结构与任务适配

“结构清晰”与“是否有 action items”不应作为所有任务共用的模糊总分，而应依据任务类型检查其专属交付。

| 任务类型 | 必要交付要素 |
| --- | --- |
| 选题构思 | 已有工作、研究缺口、候选问题、可验证假设、数据可行性与风险 |
| 方法差分 | 机制、输入条件、对比协议、优势、限制、差分主张 |
| 实验设计 | 主张—协议—指标映射、对照组、结果解释边界、补实验建议 |

可用 Code-based grader 校验报告结构、必填章节和字段；使用 rubric 型模型 grader 检查其组织、连贯性和任务适配度；抽样由研究者复核评分是否合理。

## 5. Baseline 与可归因比较

比较 DeepResearch 工作流与单轮检索—生成 baseline 时，应保持以下条件相同：

- 原始研究请求和冻结后的 ResearchBrief；
- 资料快照、模型版本、总体 token/时间预算与报告模板；
- Gold 标注与判分脚本。

Baseline 只执行一次资料检索和一次报告生成，不启用原始资料递归追溯、Critic 审阅回流或可比性校核。这样，覆盖、引用支撑和结论边界的提升才可以归因于目标工作流，而不是资料范围或任务难度变化。

可选消融实验：

| 变体 | 目的 |
| --- | --- |
| 无递归追溯 | 衡量信源追溯对来源质量和条件覆盖的影响 |
| 无 Critic 回流 | 衡量审阅闭环对引用支撑和越界结论的影响 |
| 无可比性校核 | 衡量 DataAnalyst 对指标口径混用的拦截效果 |

## 6. 研究过程质量

过程评估关注系统如何完成取证和修订，而不将“搜索次数越多”误判为研究质量越高。搜索、浏览、递归追溯和 Agent 协同的日志指标首先是可观测性信号；只有与 ResearchBrief、Gold 缺口和最终证据使用情况结合后，才构成质量指标。

### 6.1 检索效率

每项任务记录工具调用数、查询轮次、耗时和成本，并区分有效结果、空结果、失败结果和重复调用。

| 指标 | 定义 | 使用方式 |
| --- | --- | --- |
| `avg_tool_calls` | 每个任务的平均工具调用数 | 观察预算消耗，不单独代表质量 |
| `duplicate_tool_call_rate` | 参数等价的重复调用数 / 总调用数 | 检查幂等恢复和无效循环 |
| `empty_result_rate` | 返回空结果的调用数 / 总调用数 | 定位 Query 或数据源问题 |
| `latency` / `cost` | 完成一次任务的时间与调用成本 | 在满足质量门槛后比较效率 |

调用量的目标不是越低越好。若更少调用导致原始证据缺失、条件遗漏或结论越界，应判为质量下降。

### 6.2 检索广度与追溯深度

通用 Web Agent 常用独立域名数或 SERP 翻页深度衡量搜索广度；学术研究中更有意义的是研究子问题覆盖、来源类型覆盖和原始资料追溯。

| 目标 | 指标 | 说明 |
| --- | --- | --- |
| 子问题覆盖 | `subquestion_coverage` | SectionPlan 中的检索子问题，是否都获得至少一条有效 Evidence 或被明确标记为证据不足 |
| 来源广度 | `source_type_coverage` | 是否按任务需要覆盖论文、数据集、代码仓库、标准或官方文档等来源类型 |
| 来源质量 | `primary_source_rate` | 核心论断所引用证据中，原始论文、官方数据集页、官方代码仓库或标准的占比 |
| 追溯深度 | `primary_source_trace_rate` | 候选资料是否进一步追溯到原始论文、正文、实验表格、数据集或代码配置 |
| 深读充分性 | `condition_extraction_rate` | 最终被引用的核心证据中，是否提取了数据集、协议、指标等必要成立条件 |

同一论文的 arXiv 页面、出版社页面和代码仓库不应被简单视为三条独立核心论据；它们可能共同构成一条原始研究证据的不同定位入口。

### 6.3 计划、协同与状态消费

Planner 是否“拆对任务”不能用发生重试的次数代替。应基于冻结的任务要求和状态流转，检查计划覆盖与实际消费情况。

| 指标 | 定义 |
| --- | --- |
| `plan_coverage_gap_rate` | Gold 要求的研究维度中，未被 SectionPlan 覆盖的比例 |
| `redundant_subquestion_rate` | 与研究目标无关、且未产生可用 Evidence 的子问题比例 |
| `state_consumption_trace` | 记录 SectionPlan、Evidence、QuantitativeObservation、AnalysisArtifact、CriticFeedback 是否被下游对应 Agent 实际读取和使用 |
| `targeted_rework_rate` | Critic 反馈能否定位到具体章节、论断或分析产物，并被路由到相应补查、分析或修订步骤 |

协同质量的重点不是让所有 Agent 都互相传递大量文本，而是让结构化状态被正确消费：ChiefArchitect 的章节计划约束 DeepScout，DeepScout 的 Evidence 与 QuantitativeObservation 约束后续分析和写作，Critic 的反馈准确回流至对应对象。

### 6.4 自检、冲突与修正

Critic 的价值在于识别真实缺口、冲突和结论越界，并触发有针对性的回流；不能通过把所有任务都判为“需要补查”获得虚高召回。

| 指标 | 定义 |
| --- | --- |
| `gap_precision` / `gap_recall` / `gap_f1` | Critic 对 Gold 证据缺口的判断精确率、召回率与 F1 |
| `conflict_detection_rate` | 在预先标注存在冲突来源或条件不一致的任务中，成功指出冲突的比例 |
| `useful_rework_rate` | 回流后新增 Evidence、修正条件或收缩结论的任务比例 |
| `no_new_evidence_stop_rate` | 无新增有效证据时按预算停止并明确保留不确定性的比例 |

可以在少量任务中人为置入已知的冲突论文、版本差异或不可比较指标，用于检查 Conflict Detection 和结论边界，而无需等待开放网络偶然出现冲突。

### 6.5 可恢复工作流的工程验收

该组属于代码 grader 主导的确定性验收，不应与开放式研究质量混为一个总分。

- 在工具超时、进程中断和阶段恢复后，任务能从最近检查点继续；
- 同一 `Tool Call` 恢复后不会重复检索或重复写入 Evidence；
- Critic 审阅的草稿版本与 Writer 最终提交版本一致；
- 重试只发生在可恢复错误和规定预算内，失败状态被记录而非伪装为正常结果。

## 7. 业务效果

业务效果评估回答“系统是否值得继续投入”，核心由实际研究者判断。自动统计的时间和成本只能辅助说明，不能代替研究者对路线比较、验证方案和风险清单是否有用的评价。

### 7.1 对照实验设计

对同一类冻结研究任务，设置两种工作流：

| 组别 | 工作流 |
| --- | --- |
| A 组 | 研究者完全人工检索、整理资料并形成初稿 |
| B 组 | DeepResearch 生成初稿，研究者审阅、查证、修改后形成同等标准的初稿 |

首版宜采用交叉对照：不同参与者在不同但难度相近的任务上轮换 A/B 组，或同一参与者在间隔后处理不同任务，减少个人经验差异和熟悉题目带来的偏差。

实验终点固定为“可供导师、组会或技术评审讨论的可编辑初稿”，不计入完整论文撰写、真实实验实施和最终科研结论确认。

### 7.2 工作流指标

| 指标 | 定义 |
| --- | --- |
| 完成时间 | 从领取任务到形成符合固定交付要求的可编辑初稿的时间 |
| 人力成本 | 人工检索、阅读、核验和改写的投入时间；可按实际人时估算 |
| 额外查证次数 | 为确认、修正或补全系统初稿而新增的关键检索或原始资料阅读次数 |
| 修改成本 | 按重写、删除、补证、改写等动作记录的工作量，或使用预定义等级量表 |
| 可用性等级 | `可直接使用`、`轻度修改可用`、`需重写` 三档 |

“人工 3–4 小时压缩至 20 分钟”只有在资料快照、任务终点、参与者、人工修改范围均明确时才可报告；它衡量的是形成可编辑初稿的效率，不代表系统替代完整科研判断。

### 7.3 盲评质量与用户反馈

可让具备领域经验的评审只查看最终产物，不知晓其来自人工流程还是“系统初稿 + 人工修改”流程，并按以下维度评分：

- 研究问题是否聚焦；
- 技术路线比较是否完整且条件明确；
- 风险意识和结论边界是否充分；
- 验证计划是否可执行；
- 是否愿意作为后续讨论或修改的起点。

若系统进入真实团队使用，再追加长期指标：报告被引用、转发、转为汇报材料或持续复用的次数。首版离线评测不应以此类线上采用数据作为既有成果。

## 8. 当前口径

在尚未运行上述冻结任务、完成 Gold 标注和人工校准前，本文的指标均为**评测设计**，不是项目已经获得的量化成果。量化成果的具体数值必须由同一资料快照、同一任务集和固定 baseline 下的实际运行结果产生。
